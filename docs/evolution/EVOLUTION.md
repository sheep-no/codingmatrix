# Agent 引擎 13 模块演化蓝图

> 版本：v1.0 | 日期：2026-08-05 | 前置：13/13 模块深扫完成（见 [TASKS.md](TASKS.md)，各模块详档在 [modules/](modules/)）
>
> 定位：这是**演化推演**，不是修复清单。回答三个问题——每个模块现在是什么角色、未来应该演化成什么、为什么。修复（Backlog 455 项 = 13 模块 52 + 补扫 403）只是演化的**前置阻塞项**，不是终点。

## 0. 演化总图：四层模型

Agent 引擎的 13 模块按依赖方向分四层，演化目标分层定义：

```
┌─ 编排层（spec_first_generate / cross_validator / spec_first_generator）
│   现在：巨型 Mixin + 双职责混装           →   编排/生成/验证三层分离
├─ ReAct 层（react_engine / react_agent / specialist_base / error_recovery）
│   现在：设计意图被空串短路废掉             →   恢复「工具循环」并削减调用成本
├─ 工具层（executor / tools / mcp_client）
│   现在：模块级全局单例 + 竞争              →   统一工具生命周期与契约
└─ 基础设施（llm_client / llm_caller / dynamic_model_router）
    现在：双客户端路径并行 + 无成本无统一熔断  →   客户端收敛 + 可观测路由
```

核心演化判断：**当前最大负债不是单点 bug，而是「分层职责没有建立」**——spec_first_generate 一个文件同时是编排器、生成器、验证器、沙箱修复器；cross_validator 把对抗裁判和静态一致性验证混装；llm_client/llm_caller 双路径平行维护两套信号量/fallback 语义。演化优先做**职责归位**，修复优先清**归位路上的阻塞**。

## 1. 按模块演化推演

### 编排层

#### spec_first_generate.py（2383 行，最大负债）
- **当前角色**：SpecFirstGenerateMixin——编排+生成+验证+沙箱修复+重构五合一
- **演化目标**：收窄为**纯编排器**（流程控制：缓存→架构→分层生成→验证→汇报），私有方法下沉为独立服务
  - `_validate_content_syntax`（:1502）→ 独立 SyntaxValidator（按语言选语法工具）
  - `_fix_sandbox_errors`/`_recover_invalid_content`（:1811/:2003）→ SandboxRepairService（跨文件/跨路径复用）
  - `refactor_file`（:2175）→ 独立 RefactorService（非 Python 项目可复用）
- **为什么**：2383 行五职责混装导致每项都不可单测（当前零测试）。拆出后每服务独立测试，编排层只测流程
- **阻塞项（确定性见 §3）**：SPFG1（断点续传假通过）、SPFG2（JS 误判）、SPFG3（只修 .py）——不修则拆分后的验证/修复服务本身不可信

#### cross_validator.py（1512 行，§3.2 拆分对象；CV 编号体系 v1.67 重扫后重置）
- **当前角色**：双模型对抗裁判 + 跨文件静态一致性验证，混装
- **演化目标**：拆为 `CrossValidator`（对抗裁判，:63-273）+ `ConsistencyChecker`（静态一致性，:282-1512）
  - ConsistencyChecker 用 AST/language_adapter 替代正则扫描（当前正则提取假阳性密集：新 CV2 模型字段 / CV3 第三方库集合）
  - 对抗裁判的 judge 输出（reason/issues）从「丢弃」升级为「修复输入」；`is_critical_file` 子串触发（新 CV1）改为路径段全词匹配，避免普通文件被双模型交叉验证
- **为什么**：对抗与静态验证是两个演化速度不同的能力——静态验证应随 language_adapter 升级，对抗裁判应随模型能力升级，混装拖累两者
- **阻塞项**：新 CV1（is_critical_file 子串假阳性，已实测）、新 CV2/CV3（正则假阳性喂给 LLM 产生幻觉修复/幻觉缺失模块）——假阳性不修，交叉验证与修复闭环在错误输入上空转

#### spec_first_generator.py（536 行）
- **当前角色**：架构师角色生成器（OpenAPI→类型→DB→配置）
- **演化目标**：升级为**规范-实现契约的权威来源**——返回值语义与「全部成功」对齐（SFG1），OpenAPI 步骤走 model_config（SFG3），作为编排层唯一的规范生成入口（现 refinement_loop/incremental_modify/spec_first_generate 三处消费，复用点已稳定）
- **为什么**：它是全引擎最干净的「生成器」角色样本，应作为编排层拆分的模板
- **阻塞项**：SFG1（返回值语义）、SFG3（配置未生效）

### ReAct 层

#### react_engine.py（§13 认知修正：真引擎）
- **当前角色**：ReAct 工具循环唯一实现（full），但 project_path 空串短路（RE1）使 full 路径退化为单次 LLM 调用
- **演化目标**：恢复设计意图——project_path 正确注入（RA2 根因修复）→ 工具可用 → `success` 从「恒 False」（RE4/RE3）升级为「工具执行语义」；同步工具加超时（RE3）；result_count 从恒 0（RE4）升级为真实统计
- **为什么**：它是 specialist_base/agent_executor/task_planner/react_agent 四个使用方的共同引擎——恢复它等于同时恢复四条路径
- **阻塞项**：RE1（空串短路，已实测）、RE2（工具契约）、RA2（context 未用）

#### react_agent.py（190 行薄包装）
- **当前角色**：ReActEngine 的包装入口（process → engine 双入口之一）
- **演化目标**：确认「一个引擎两个入口」定位（§13），删除与引擎重复的状态管理（RA1/RA2），process 的 context 参数真正透传
- **为什么**：它是 error_recovery 生产调用点——修正这里直接打通自动修复链
- **阻塞项**：RA2（context 未用，自动修复链根因）

#### specialist_base.py
- **当前角色**：full 模式每轮 4 次 LLM 调用 × 3 轮 = 12 次，且无 memory 传递（SB1）
- **演化目标**：full 模式调用次数收敛——每轮降为 1 次核心调用 + 工具结果回流，memory 链传递；`_REACT_MODE` 从固定 full 恢复为可配置（SB2 测试断裂同步修复）
- **为什么**：成本（LC1/DMR1）与调用次数是同一面——先降调用数再谈成本统计
- **阻塞项**：SB1（12 次/轮）、SB2（测试收集失败）

#### error_recovery.py（子包，33 行）
- **当前角色**：测试失败→ReAct 修复→复测的闭环入口，但闭环完全失效（ERR1+ERR2：context 被忽略→短路→success 恒 False）
- **演化目标**：成为 ReAct 层的**验证消费者**——修复后必须复测（`_run_dynamic_tests`）才算完成，返回结构化结果（未尝试/失败原因，ERR3）；与顶层 ErrorRecoveryLoop（797 行，待补扫）组成「测试修复」与「内容修复」两条线
- **为什么**：它的存在证明引擎设计了「生成-测试-修复」闭环，只是被短路废掉——修复后是整个系统最直接可验证的价值点
- **阻塞项**：RA2（根因）、RE1（短路）

### 工具层

#### executor.py
- **当前角色**：ToolRegistry 模块级全局单例，工具注册/同步包装
- **演化目标**：ToolRegistry 从闭包捕获 project_path（B1）演化为**显式注入的上下文对象**；与 MCPClientManager（MCP1）统一为同一工具生命周期管理（注册→启用→失效→清理）
- **为什么**：两个「全局单例」+两个「MCP 工具来源」是工具层不稳定的根源——演化目标是单一工具注册表 + 单一生命周期
- **阻塞项**：B1（单例闭包，已实测）、MCP1/MCP2（单例竞争）

#### tools.py
- **当前角色**：20 个内置工具 + Python 沙箱执行 + 路径白名单
- **演化目标**：沙箱从「正则黑名单+静态检测」（T6）演化为**独立 SandboxExecutor**（AST 白名单 + 真实路径校验 + 超时隔离）；cwd 校验从前缀匹配（T2）升级为规范路径解析；`set_allowed_file_paths` 从模块级全局（T5）改为工具上下文传递
- **为什么**：沙箱是工具层安全基底，静态正则黑名单的绕过性使其只能算临时方案
- **阻塞项**：T1（os NameError，已实测）、T2（前缀绕过）、T6（黑名单可绕过）

#### mcp_client.py
- **当前角色**：MCPClientManager 全局单例，4 处使用方 2 种获取方式竞争
- **演化目标**：演化为**连接生命周期管理器**——单例统一（MCP1）、工具闭包绑定连接对象（MCP2）、HTTP 分支补标准握手（MCP3）；作为 executor 工具注册表的一个**工具源插件**，而非平行单例
- **为什么**：MCP 是外部工具源，其生命周期（连接/断开/失效）应被工具层统一管理，而非各自为政
- **阻塞项**：MCP1/MCP2（单例竞争）、MCP3（HTTP 非标准）

### 基础设施

#### llm_client.py / llm_caller.py（双路径）
- **当前角色**：LLMClient（class，specialist_base/spec_first_generate 用）与 call_llm（函数，26 文件直连）双路径并行，各自维护信号量/fallback 语义（且两处都有缺陷：LC2/LC5 + LCL1/LCL2）
- **演化目标**：**客户端收敛**——call_llm 降为 LLMClient 的薄函数适配（或 LLMClient 重写为 call_llm 的异步核心），信号量/超时/fallback/成本统计单点实现；语义差异（LCL2 fallback 用 primary config、LCL3 键不一致）收敛为一份契约
- **为什么**：双路径是信号量缺陷双出现（§10.1）的直接原因——一份契约、一份实现、一份测试
- **阻塞项**：LCL1（信号量顺序+泄漏，P0）、LCL2（fallback config 错）、LC1（成本恒 0）

#### dynamic_model_router.py
- **当前角色**：进程内模型路由单例（熔断/学习/配置/上下文）
- **演化目标**：升级为**可观测路由基础设施**——成本字段补齐（DMR1，与 LC1 同一修复）、熔断阈值统一（DMR2）、DB 路径可配置（DMR9）、roles 缓存策略统一（DMR7）；学习路由从恒探索（DMR5）演化为收敛式探索
- **为什么**：它是 llm_client/llm_caller 收敛后的路由依赖——客户端收敛后，路由的决策质量直接决定全引擎模型选择
- **阻塞项**：DMR1（成本字段，LC1 根因）、DMR2（阈值统一）

## 2. 演化优先级（三步走）

- **阶段一 · 解阻塞（P0/P1 实测与实码可证项）**：RA2+RE1（恢复 ReAct 循环）→ LCL1（信号量）→ B1+T1（工具层稳定）→ MCP1（单例统一）——这五条是四层各自的根，不修则上层演化无立足点
- **阶段二 · 职责归位**：spec_first_generate 拆服务 → cross_validator 拆双类 → llm 客户端收敛 → 沙箱独立——对应本文档四层演化目标，每步伴随测试补全
- **阶段三 · 能力升级**：对抗裁判用 judge 输出驱动修复、学习路由收敛式探索、成本统计接入预算控制——依赖阶段一/二的结构

## 5. 参考 LangGraph / LangChain 的演化路径校准

> 依据 2026-08-05 官方文档实测（docs.langchain.com：workflows-agents / persistence）。用 LangGraph/LangChain 的成熟模式**校准**本引擎的演化目标——不是照搬，是确认演化方向与业界已验证的模式一致，并指出可直接借鉴的实现形态。

### 5.1 ReAct 层 → LangGraph Agent 模式（三节点 + 条件边）

**LangGraph 已验证模式**：`llm_call` 节点 ↔ `tool_node` 节点 + `should_continue` 条件边；循环/终止的**唯一判定标准**是「最后一条消息是否有 tool_calls」；工具结果作为 `ToolMessage`（带 `tool_call_id`）回流消息历史。

| 校准对象 | LangGraph 参考 | 演化含义 |
|---------|---------------|---------|
| react_engine 单循环模型/工具混步 | llm_call / tool_node 显式分离 | 拆为「模型决策 / 工具执行 / 终止判定」三态——对应 RE4（result_count 恒 0）与 RA3（success 仅看 action）的修正方向 |
| success 判定缺陷（RE3/RA3） | `if last_message.tool_calls: return "tool_node" else: return END` | 终止判定从「模型自报完成」改为「无 tool_calls 即结束」，**消除 success 恒 False 的语义黑洞** |
| react_engine 自维护对话历史 | MessagesState + add_messages reducer | 消息历史用标准 Message/ToolMessage 结构（tool_call_id 关联），为 memory 传递（SB1）与观测铺路 |

### 5.2 编排层 → Evaluator-optimizer 与 Orchestrator-worker

**LangGraph 已验证模式**：
- Evaluator-optimizer：生成节点 → 评估节点 → 条件边「Rejected+Feedback → 生成节点 / Accepted → END」——迭代直到达标
- Orchestrator-worker（`Send` API）：orchestrator 规划 → 每个 section 一个 worker（独立 state）→ 各 worker 写入共享 state key → synthesizer 合成

| 校准对象 | LangGraph 参考 | 演化含义 |
|---------|---------------|---------|
| spec_first_generate 线性 if 脚本 + 散落验证分支 | Evaluator-optimizer 显式图 | 文件生成收敛为 subgraph「generate→validate→repair 条件回边」——`_validate_content_syntax`/`_fix_sandbox_errors` 成为图节点而非 if 分支，每个节点独立可测 |
| refinement_loop while 循环 + 字符串操作 | 生成/评估节点 + Feedback schema | 用「结构化 Feedback + 条件回边」替代隐式 while——修复是否达标的判定显式化（对应 CV10 修复后不验证、SFG2 半规范继续） |
| 分层生成 asyncio.gather + cross_validator 一致性 | Send API + 共享 completed_sections key | 每文件生成 = worker（独立 state），一致性验证 = synthesizer（读共享 state）——与 cross_validator 拆分（§1）的形态一致 |
| `_generate_missing_modules` 幻觉生成缺失模块（新 CV3） | Send API 动态创建 worker | 缺失模块 = 动态 worker 节点，且生成前复核第三方库白名单（避免把第三方库当缺失模块） |

### 5.3 工具层 → @tool 抽象 + ToolNode + ToolRuntime 注入

**LangGraph/LangChain 已验证模式**：
- `@tool`：name/description/args_schema 从函数签名自动推导
- `ToolNode`：统一工具执行，并行、错误处理、状态注入
- **`ToolRuntime`**：工具读图 state 和 run-scoped context 的方式是**运行时显式注入**（`runtime.state["user_id"]`），官方明确「read state and run-scoped context from ToolRuntime」——而非闭包捕获

| 校准对象 | LangGraph 参考 | 演化含义 |
|---------|---------------|---------|
| tools.py params 字符串描述（:364 `"string (desc)"`） | @tool 自动推导 args_schema | 演化为 JSON Schema——直接解决 MCP7（参数无 schema 校验全字符串透传） |
| executor ToolRegistry 闭包捕获 project_path（B1） | ToolRuntime 显式注入 | **官方模式就是 B1 的反面教材**——project_path 应注入工具运行时而非闭包捕获；MCP2（闭包依赖全局 _instance）同理 |
| 双全局单例（ToolRegistry + MCPClientManager） | ToolNode 集中工具执行 | 统一为单一工具执行节点，MCP 工具作为其工具源 |
| 工具返回契约混装（success/error/业务数据） | ToolMessage（content + 结构化） | 返回结构化内容块，语义统一 |

### 5.4 基础设施 → Checkpointer / Store 持久化模型

**LangGraph 已验证模式**：
- **Checkpointer**：持久化图状态快照（thread_id），用于故障恢复（fault tolerance）、time travel、human-in-the-loop
- **Store**：跨线程长时记忆（用户偏好/事实/共享知识），需**剪枝策略**（文档明确「Checkpoints growing unboundedly → prune」）
- 生产持久化：MemorySaver（内存，重启丢失）→ 生产用 SqliteSaver/PostgresSaver

| 校准对象 | LangGraph 参考 | 演化含义 |
|---------|---------------|---------|
| SPFG1 断点续传「>10 字节文件存在即跳过」 | Checkpointer 图状态快照 + thread_id | 断点续传 = **显式检查点**（生成进度状态），而非文件启发式判断——根治假通过 |
| SPFG8 spec_cache 无失效 | Store 需剪枝/保留策略 | 缓存状态带失效策略与保留窗口 |
| DMR9 DB_PATH 硬编码 /tmp（重启丢失） | MemorySaver vs SqliteSaver | 「内存级不持久」问题已有生产解法——可配置持久化路径，学习路由数据跨重启保留 |
| LC1/DMR1 成本恒 0、无 trace | LangSmith 观测（文档强调 tracing 检测问题） | 客户端收敛后加观测层（token/成本/延迟 span） |

### 5.5 校准结论

- **方向确认**：本蓝图 §1 的四层演化目标与 LangGraph/LangChain 已验证模式**高度一致**——编排层图形化、ReAct 层三态化、工具层注入化、持久化显式化，均在业界成熟框架中有对应实现形态
- **可直接借鉴的实现形态**：Evaluator-optimizer（生成-评估条件回边）、ToolRuntime 注入（替代闭包捕获）、Send API 动态 worker（替代死代码分支）、Checkpointer+thread_id（替代文件启发式断点）
- **差异化**：LangGraph 面向通用 agent 状态图，本引擎面向代码生成编排——校准重点是**终止判定语义化、验证闭环图形化、状态注入显式化**三项，不引入通用图运行时（保持当前轻量 Mixin 结构，仅按此模式重构内部组织）

### 5.6 五支柱结构延伸：产物协议 + 阶段门禁 + 检查点

> 依据 2026-08-09 全库补扫（Backlog 255 项）对 §5.1-5.5 的深化。LangChain 值得仿照的不是类体系，是三个抽象原则：**统一协议（Runnable）、显式控制流（LangGraph 状态图）、横切关注点外置（Callbacks/Checkpointer/Store）**。本引擎与 LangChain 的根本差异：它面向通用对话/工具 agent，本引擎面向「需求 → 可验证代码」流水线——所以抽象不是「链 + 消息」，而是「产物协议 + 阶段门禁 + 检查点」。

**目标结构**：

```
Session（= 一个图实例，session_id = thread_id）
│
│  Spec ──▶ Architecture ──▶ FilePlan ──▶ FileBatch ──▶ VerifiedCode ──▶ Report
│   │            │               │             │              │
│   └────Gate────┘               └─────Gate────┘              │
│                                                              │
│  横切层：Tracing / Cost / Events（统一通道，不侵入节点）      │
│  Checkpointer：每节点执行后写检查点，断点续传 = 从检查点重入   │
│  共享真相源：DependencyGraph（全库唯一实例，读同一份图）      │
```

五支柱与 Backlog 主线的对应：

| 支柱 | 目标形态 | 消化/依赖的 Backlog |
|------|---------|---------------------|
| 1. 产物协议 | 全链共享结构化中间产物（schema + content_hash + 来源）；两套增量、四套验证器以它为收敛基准 | SM2/SM3（hash 从死能力变产物属性）、CV8、两套增量、三处 API 校验 |
| 2. 阶段 = Transform，验证 = Gate | 每阶段后内置门禁，返回结构化 Verdict（通过/拒绝+反馈）；验证内建而非链尾一次性 | 「存在≠正确」主线（TG2/TR1/IM2/RL3/FD2）、CV10、SFG2 |
| 3. Checkpointer | 断点续传 = 从检查点重入，根治文件启发式 | SPFG1、SM10（DB 不同步面）、SM2/SM3 |
| 4. 共享真相源 | DependencyGraph 全库唯一实例，影响传播/缺失补充读同一份图 | OA12/DG1/DG3/AR8 闭环、IA3（影响传播） |
| 5. 横切层外置 | tracing/cost/events 统一通道，不侵入业务组件 | TT1、OP1（成本恒零）、OP2 |

**演化顺序（协议先行）**：
1. 统一低层契约：LLM 契约收敛（LCL1）→ 验证器协议（CV8）→ 产物 schema——所有接线失败源于契约不一致，这是前提
2. 收敛重复实现：两套增量、两套错误恢复、三处 API 校验，以统一产物协议为基准
3. 显式化状态与控制流：Session → Checkpointer、断点续传 → 检查点重入
4. 接死代码：dependency_graph 共享实例、测试选择链（OT16/IA3/TS1/TS6/FC2）、跨文件补丁（CP10/OF10）

**一句话落地**：用 LangChain 的「协议 + 图 + 横切」三原则，替换通用消息抽象，换成代码生成专属的「产物 + 门禁 + 检查点」——§0/§1 四层演化目标与 §5.1-5.5 校准结论均已指向此形态，按 Backlog 顺序先把契约钉死。
